# 架构与设计

ProofBI 的目标不是“让模型会写 SQL”，而是让业务同学**敢用**自然语言问出来的数字：口径统一、权限不漏、每个数字可以核对。这份文档按一个问题经过的链路，解释每一步的设计和取舍。

## 1. 模块划分

| 模块 | 路径 | 职责 |
|---|---|---|
| 虚构数据 | `app/warehouse/generate.py` | 固定种子生成约 10.6 万行零售数据，写入后计算数据集指纹 |
| 语义层 | `app/semantic/layer.py`、`semantic/retail.yaml` | 加载并校验指标、维度、表与关联；不一致时启动失败 |
| 时间解析 | `app/semantic/timeparse.py` | 相对时间按语义层的“今天”解析成具体日期；判断是否超出数据范围 |
| 编译器 | `app/semantic/compiler.py` | 计划 → 一条或多条 SQL（模板 SQL 写手） |
| 权限 | `app/semantic/access.py`、`semantic/access.yaml` | 演示用户、数据范围、行级策略模板 |
| 规划器 | `app/agent/planner.py`、`llm_components.py` | 问题 → 计划 / 澄清 / 拒答；规则版和 LLM 版共用确定性筛查与校验 |
| SQL 安全 | `app/sqlsafe/guard.py`、`rls.py`、`executor.py` | 三道防线：AST 校验、行级权限改写、只读执行 |
| 口径校验 | `app/sqlsafe/lint.py` | 模型写的 SQL 是否算的是计划要的那个指标 |
| 结论与核对 | `app/agent/narrator.py`、`verifier.py`、`numbers.py` | 生成结论与图表规格；逐个核对数字 |
| 流水线 | `app/agent/pipeline.py`、`tracing.py` | 事件生成器，串起所有步骤并记录链路 |
| 持久化 | `app/models.py`、`repository.py` | 对话、运行、每次 SQL 尝试、链路、评测结果 |
| 评测 | `app/evals/` | 结果集比对、评分、CLI 门禁 |

## 2. 数据集

Leon优选是一个虚构的零售连锁：7 个区域、24 家门店（其中 2 家在统计期内开业）、12,000 名会员、240 个商品、约 3.4 万笔订单和 6 万条订单明细，时间跨度 2024-10-01 至 2026-09-30。

几个刻意的设计：

- **订单状态有三种**：paid、refunded（整单退款）、cancelled（未支付取消）。GMV 不含 cancelled，这让“漏掉状态过滤”成为一个真实会算错的口径问题。
- **优惠按比例分摊到明细**，最后一行补差，保证同一订单的明细实付之和精确等于订单实付。因此“按品类拆分的 GMV 之和 = 总 GMV”可以作为编译器不重复计算的测试。
- **有可分析的结构**：西南增长最快、东北基本持平，华南退款率偏高，双十一和 618 有峰值，线上渠道份额逐年上升。
- **手机号是明显的假号码**（100 开头），并且是敏感字段，任何人都不能查询。
- **确定性**：同一个种子和生成器版本得到逐行相同的数据和相同的指纹；评测的标准答案因此不会漂移。

## 3. 语义层

`retail.yaml` 是口径的唯一来源。每个指标包含：

```yaml
gmv:
  label: GMV
  description: 已支付订单的实付金额合计。包含之后整单退款的订单，不包含已取消（未支付）订单。
  expr: ROUND(SUM(o.pay_amount), 2)
  item_expr: ROUND(SUM(oi.pay_amount), 2)   # 按品类 / 品牌 / 商品拆分时使用
  filter: o.status IN ('paid', 'refunded')
  synonyms: [GMV, 成交额, 交易额, ...]
  lint: {status: [[paid, refunded]], sum_of: pay_amount}
```

设计要点：

- **粒度与扇出**。关联只允许从“多”走向“一”（明细 → 订单 → 门店 / 区域 / 会员）。需要按品类拆分时，基表换成订单明细，指标改用 `item_expr`（分摊后的实付）；只用 `COUNT(DISTINCT ...)` 的指标天然不怕扇出，可以直接复用。复购率这种需要“先按客户聚合再算比例”的指标，不支持按品类拆分，会直接说明原因。
- **过滤条件不同的指标分开查**。GMV 统计 paid + refunded，毛利只统计 paid。一个问题同时问到两者时编译成两条查询（q1、q2），各自有自己的溯源。
- **比率指标同时返回分子和分母**（客单价 = GMV ÷ 下单用户数）。回答里出现的分子分母也能被核对。
- **歧义词显式登记**。“销售额 / 营收 / 业绩”同时对应 GMV 和净销售额，规划器不猜，返回澄清选项；用户选择后带着 `clarifications` 重新提问。
- **加载即校验**。表达式无法解析、引用未声明的表别名、歧义词指向不存在的指标都会让启动失败；启动时还会用数据核对维度枚举值（例如区域列表），口径和数据对不上就不启动，避免“筛选条件永远匹配不到”这种静默错误。

> 一个踩过的坑：关联条件最初写成 `{from: ..., to: ..., on: "..."}`，结果 PyYAML（YAML 1.1）把键 `on` 解析成了布尔值 `True`。现在键名是 `condition`。

## 4. 问题解析（规划器）

输出三种结果之一：**计划**（指标、维度、筛选、时间、对比、排序）、**澄清**、**拒答**。

确定性筛查先于任何模型：写操作、敏感字段、明细导出、预测类问题直接拒答；歧义词直接澄清。随后：

- **规则规划器**（离线模型）：在语义层词表上做“最长优先”的匹配（“毛利率”优先于“毛利”，“上海徐汇店”优先于“上海”），再处理分组词（各 / 按 / 哪个）、排名词（前 N / 最高）、对比词（环比 / 同比）和追问（“那华南呢？”继承上一问的指标和时间，只替换筛选）。
- **LLM 规划器**：把指标、维度、取值和用户的数据范围放进提示词，要求输出 JSON；未知指标或不合法 JSON 带着错误重试一次，再失败回退到规则规划器。模型只输出时间原文（例如“上个月”），具体日期仍由代码解析。

两者的计划都经过同一个 `validate_plan`：指标是否存在、成本类指标是否有权限、维度能否拆分、筛选值是否合法，以及**筛选的区域 / 门店 / 城市是否在用户的数据范围内**。越权在这一步就拒答，并说明原因——如果只靠行级权限，Mia 问华南会得到一个“0”，这比拒答更糟。

## 5. 生成 SQL 与自我纠错

每条查询最多尝试 `1 + max_corrections`（默认 3）次：

```
写 SQL → 安全校验 → 口径校验 → 行级权限改写 → 执行
          │可修复      │不一致                       │报错
          └────────────┴───────── 带着错误信息重写 ───┘
          │安全违规 → 直接拒答，不重试
```

- **可修复**：语法错误、未知的表 / 字段 / 函数、`SELECT *`、无条件 JOIN、口径不一致、执行报错（例如 `no such column: o.amount`）。错误信息原样交回写手。
- **不可修复（安全违规）**：多语句、非 SELECT、系统表、表函数、敏感字段、危险函数、递归 CTE。重试只会给攻击者更多次机会，所以直接拒答。执行层授权回调拒绝某个操作也按安全违规处理——这说明有东西绕过了前两层。

离线模式下 SQL 由编译器生成；管理员可以在控制台开“演示故障”，让第一次生成故意犯一个典型错误（不存在的字段、漏掉状态过滤、月末少一天、读取手机号、把数字写错），用来演示和测试纠错、口径校验、安全拦截和数字核对。

## 6. 口径校验（lint）

安全的 SQL 仍可能回答了另一个问题。口径校验在 AST 上只看 WHERE 子句（`CASE WHEN status = 'refunded'` 属于指标公式，不是过滤）：

- **订单状态**：计算 WHERE 允许通过的状态集合，与指标声明的可接受集合比较。`status <> 'cancelled'`、`status IN ('paid', 'refunded')`、`NOT status IN ('cancelled')` 是同一个集合，都通过；漏掉过滤或只统计 paid 则不通过。
- **求和字段**：GMV 必须对 `pay_amount` 求和，而不是 `gross_amount`。
- **时间范围**：把 BETWEEN、比较运算、`SUBSTR(order_date, 1, 7) = '2026-09'`、`LIKE '2026-09%'` 都归一成日期区间（对比查询是两个区间的并集），和计划比较；`DATE('now')` 直接不通过，因为它让结果随运行日期变化、无法复现。
- **筛选值**：计划里的每个筛选值（或其编码，例如华东 → east）都必须出现在 WHERE 中。

字段名本身拼错（`o.amount`）不归口径校验管，交给执行器报出更准确的 `no such column`。

## 7. 行级权限：改写而不是提示

`apply_row_policies` 先收集查询里所有物理表引用，再把每一个替换成策略视图：

```sql
-- 原始：FROM orders AS o
FROM (SELECT channel, customer_id, ..., store_id FROM orders WHERE region_id IN ('east')) AS o
```

- 条件来自登录用户在 `access.yaml` 中的数据范围（区域 / 门店），值由 sqlglot 构造成字面量后再解析，不做字符串拼接。
- 视图只投影该用户可读的字段，敏感字段在查询作用域里根本不存在。
- 订单明细、会员没有区域字段，用子查询表达（例如会员 = 在本区域下过单的会员），所以 JOIN 之后的维度拆分依然一致。
- 管理员也会被包一层（只做字段投影，不加行条件），敏感字段对所有人都不可见。
- 改写后的 SQL 与原 SQL 一起保存；控制台的“实际执行的 SQL”标签把系统加入的条件高亮出来。

## 8. 执行

只读打开 SQLite（`mode=ro`）并设置 `PRAGMA query_only`，再挂一个授权回调：只放行 SELECT、白名单表的白名单字段、白名单函数。进度回调在超时（默认 3 秒）时中止查询，最多取 `max_rows + 1` 行用于判断是否截断。每次执行记录：

- `sql_hash`：实际执行 SQL 的 sha256；
- `result_hash`：列名和结果行的 sha256；
- 数据集指纹、执行时间、耗时、行数、是否截断、生效的行级策略。

“重新执行并比对”先确认存储的 SQL 与 `sql_hash` 一致（防止记录被改），重新做一次安全校验，再执行并比较结果指纹。

## 9. 结论、图表与数字核对

离线结论由模板生成，数值统一格式化（金额 ≥ 10 万用“万元”、同一列统一单位；比率保留 1 位小数的百分比；整数加千分位）。图表只是规格（类型、x、y、系列），由控制台用同一份结果行绘制：单指标 → 指标卡，按时间 → 折线，按类别 → 条形，本期 vs 对比期 → 对比卡或分组条形（本期用品牌色，对比期用灰色）。

数字核对（`verifier.py`）：

1. 抽取回答中的数字；日期、排名（前 5）、时长（近 30 天）以及结果里本身就是文本的标签（如“25-34岁”）先遮住，不当成数据检查。
2. 按回答自身的精度给出容差：“17.9%”对应 0.179 ± 0.0005，“13.36 万元”对应 133,600 ± 50。能和某个结果单元格对上 → **一致**，记录查询、行、列。
3. 对不上时检查是否是公开的简单推算：同一列两格之间的变化率、百分点差、差值，占比，合计，行数 → **推算**，记录公式和用到的单元格。
4. 都不是 → **无法核对**，控制台标红，整条回答的核对结论为失败。

LLM 写的结论走同一套核对。核对只证明“数字来自结果”，不证明文字的推理正确；推算规则也故意保持很少，避免把巧合当成依据。

## 10. 链路与持久化

流水线是一个事件生成器：控制台通过 SSE 实时看到每一步；结束时产出 `RunRecord`，保存为运行、每次 SQL 尝试（包括被拒绝和报错的）和链路节点。被拒绝的尝试同样是证据：评审时能看到模型第一次写错了什么、系统是怎么拦下的。

## 11. 可替换的部分

| 部分 | 当前实现 | 生产环境的替换 |
