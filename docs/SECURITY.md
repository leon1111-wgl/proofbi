# 安全设计

ChatBI 把“写 SQL”交给了一个会被提示注入、会幻觉的组件。ProofBI 的原则是：**模型输出的 SQL 是不可信输入**，安全不依赖提示词，而是由代码在三个独立的层上强制执行，任何一层单独失效都不应造成越权。

## 威胁模型

| 威胁 | 例子 | 主要防线 |
|---|---|---|
| 破坏性语句 | `DROP TABLE`、`DELETE`、`UPDATE`、`ATTACH`、`PRAGMA` | ① AST 只允许单条 SELECT；③ 只读连接 + 授权回调 |
| 语句堆叠 | `SELECT 1; DROP TABLE orders` | ① 多语句直接拒绝 |
| 读系统信息 | `sqlite_master`、`pragma_table_info()`、`sqlite_version()` | ① 系统表 / 表函数 / 函数白名单；③ 授权回调 |
| 读敏感字段 | `SELECT phone FROM customers`、`ORDER BY phone` | ① 敏感字段黑名单；② 策略视图不投影；③ 授权回调拒绝读取 |
| 越权读数据 | 华东经理查华南、提示“忽略权限” | 问题层拒答；② 每个表引用替换成带行条件的策略视图 |
| 绕过行级权限 | 子查询、CTE、UNION、EXISTS、别名伪装、大小写 / 引号变体 | ② 对 AST 中所有物理表引用统一改写 |
| CTE 遮蔽 | `WITH orders AS (...) SELECT ... FROM orders` | ① CTE 与物理表重名直接拒绝 |
| 资源耗尽 | 笛卡尔积、`WITH RECURSIVE`、`randomblob(1e9)`、超大 LIMIT | ① 禁止无条件 JOIN 与递归 CTE、函数白名单、LIMIT 上限；③ 超时中止、取行上限 |
| 注释 / 格式花招 | `/* ; DROP ... */`、`--` | ① 执行的是 AST 重新生成的 SQL，注释被去掉 |
| 加载扩展 / 读文件 | `load_extension()`、`readfile()` | ① 危险函数黑名单（安全违规）；③ 授权回调 |
| 篡改历史记录后重放 | 修改数据库里保存的 SQL | 重放前校验 SQL 指纹，并重新做一次安全校验 |
| 成本数据泄露 | 区域经理查毛利率、`unit_cost` | 问题层指标权限；①② 字段权限（`requires: cost`） |

## 第一道：AST 静态校验（`app/sqlsafe/guard.py`）

用 sqlglot 按 SQLite 方言解析，遍历整棵树：

- 恰好一条语句，且根节点是 SELECT 或集合运算（UNION / INTERSECT / EXCEPT）。
- 不出现任何写入 / 定义 / 事务 / PRAGMA / ATTACH / `SELECT ... INTO` 节点。
- 表必须在白名单中；不允许库名前缀、系统表（`sqlite_*`、`pragma_*`）、内部表（`dataset_meta`）和表函数；CTE 不能与物理表重名；禁止 `WITH RECURSIVE`。
- 函数白名单（聚合、ROUND、COALESCE、SUBSTR、STRFTIME、窗口函数等）。不在白名单的函数默认是可修复错误（例如模型写了 PostgreSQL 的 `DATE_TRUNC`），已知危险的函数是安全违规。
- 禁止 `SELECT *` 和 `t.*`（`COUNT(*)` 可以）；敏感字段和无权限字段在任何位置出现都拒绝。
- 每个 JOIN 必须有“字段 = 字段”的条件；逗号连接、CROSS / NATURAL JOIN、`ON 1 = 1` 都拒绝。JOIN 数有上限，SQL 长度有上限。
- LIMIT 必须是整数常量；缺失时补上上限，超过上限时收紧。
- 规范化后的 SQL 会被再解析一次，确认仍然是单条 SELECT（防止解析器与生成器之间的差异）。

> sqlglot 30 的两个细节：`AND` / `OR` 也是 `exp.Func` 的子类，函数白名单检查时要排除连接词；不带条件的 `JOIN x` 会被解析成 `ON TRUE`，所以“缺少关联条件”要检查是否存在字段等值，而不是检查 ON 是否为空。

## 第二道：行级权限改写（`app/sqlsafe/rls.py`）

先收集所有物理表引用，再统一替换为策略视图（只含允许字段，WHERE 来自登录身份）。先收集再替换，保证策略里引用的表（例如订单明细策略中的 `orders`）不会被再次包裹。条件模板中的 `{regions}` / `{stores}` 用 sqlglot 构造的字符串字面量展开，用户数据范围的编码在加载时还会做格式校验。

这一层不依赖模型是否“听话”：即使模型照着注入写出 `WHERE region_id = 'south' OR 1 = 1`，它查询的 `orders` 已经只剩华东的行。

## 第三道：执行层（`app/sqlsafe/executor.py`）

- `file:...?mode=ro` 打开 + `PRAGMA query_only = 1`；
- SQLite 授权回调：只放行 `SQLITE_SELECT`、白名单表的白名单字段读取、白名单函数，其余（包括 PRAGMA、ATTACH、写操作、递归）一律拒绝；被拒绝时记录原因；
- 进度回调实现超时（默认 3 秒）；最多取 1000 行。

授权回调拒绝任何操作时，流水线按安全违规处理并拒答，因为这意味着有东西绕过了前两层。

## 已知局限

- **聚合推断**：行级权限防不住在自己权限范围内用很细的筛选反推个人信息（差分攻击）。生产环境应加最小分组人数（例如少于 5 人的分组不返回）和查询审计。
- **SQLite 特有能力**：授权回调和进度回调是 SQLite 的能力。换到 ClickHouse / StarRocks 时，第三道防线要换成数据库只读账号、行级策略和资源组；前两道防线可以直接复用（sqlglot 支持这些方言）。
- **计时侧信道**：没有对执行时间做任何遮蔽。
- **演示身份**：登录用演示账号和固定密码，仅用于本地演示；`PROOFBI_DEMO=0` 时登录页不展示账号。生产环境应接企业 SSO。
- **结论的推理**：数字核对证明数字来自结果，不证明文字推理正确（例如因果判断），所以离线结论模板不做归因，LLM 提示词也要求“不推测原因”。
